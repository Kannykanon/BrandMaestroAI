# Alembic Migration Guide

A reference for setting up and using Alembic for database schema management.  
Use this instead of `Model.metadata.create_all()` in staging and production.

---

## Why Alembic

| `create_all()` | Alembic |
|----------------|---------|
| Blindly creates tables | Tracks every schema change in order |
| No version history | Full version history, like Git for your DB |
| Cannot roll back | Can upgrade and downgrade |
| Not safe in production | Production standard |

---

## One-Time Setup

### 1. Install

```bash
pip install alembic
```

### 2. Initialise Alembic in your project root

```bash
alembic init alembic
```

This creates:

```
your-project/
├── alembic/
│   ├── env.py        ← configure db connection and models here
│   └── versions/     ← generated migration files live here
└── alembic.ini       ← main config file
```

### 3. Configure `alembic.ini`

Set your database URL:

```ini
sqlalchemy.url = postgresql://user:password@localhost/your_db
```

For environment variable support (recommended for production):

```ini
sqlalchemy.url = %(DB_URL)s
```

Then set `DB_URL` in your `.env` file.

### 4. Configure `alembic/env.py`

Point Alembic to your SQLAlchemy models. Find the line that says `target_metadata = None` and replace it:

```python
from database import Model  # import your SQLAlchemy base

target_metadata = Model.metadata
```

### 5. Remove `create_all()` from your codebase

```python
# Remove this from main.py or db.py
Model.metadata.create_all(engine)
```

Alembic manages your schema from now on.

## Daily Workflow

### Step 1 — Make your model change

Add, modify, or remove a column or table in your SQLAlchemy models as normal.

### Step 2 — Generate a migration

```bash
alembic revision --autogenerate -m "describe your change here"
```

Examples:
```bash
alembic revision --autogenerate -m "add balance column to users"
alembic revision --autogenerate -m "create transactions table"
alembic revision --autogenerate -m "add index on email"
```

This generates a file in `alembic/versions/`. **Always review it before running.**

### Step 3 — Review the generated file

```python
def upgrade():
    op.add_column('users', sa.Column('balance', sa.Numeric(), nullable=True))

def downgrade():
    op.drop_column('users', 'balance')
```

Check that:
- The `upgrade()` does what you intended
- The `downgrade()` cleanly reverses it
- No unintended table drops or renames

### Step 4 — Apply the migration

```bash
alembic upgrade head
```

`head` means the latest version.

### Step 5 — Commit the migration file

```bash
git add alembic/versions/
git commit -m "migration: add balance column to users"
```

Migration files belong in version control alongside the code change that required them.

## Common Commands

```bash
# Apply all pending migrations
alembic upgrade head

# Roll back one migration
alembic downgrade -1

# Roll back to a specific version
alembic downgrade <revision_id>

# Check current migration version
alembic current

# View migration history
alembic history

# Generate empty migration (for manual changes)
alembic revision -m "manual change description"
```

---

## Initial Migration for Existing Models

If you already have SQLAlchemy models and are adding Alembic for the first time:

```bash
# Generate migration from your existing models
alembic revision --autogenerate -m "initial tables"

# Review the generated file, then apply
alembic upgrade head
```

If the tables already exist in the database, stamp the current state so Alembic doesn't try to recreate them:

```bash
alembic stamp head
```

---

## Production Deployment

Never run migrations manually in production. Wire them into your CI/CD pipeline:

```bash
# In your deployment script or Dockerfile entrypoint
alembic upgrade head && uvicorn main:app --host 0.0.0.0 --port 8000
```

This ensures the database is always migrated before the app starts.

---

## Rules

- Never edit a migration file after it has been applied to any environment
- Never delete migration files
- Always review autogenerated migrations before running — Alembic can miss renames and misinterpret some changes
- One migration per feature or change — keep them small and focused
- Migration files are part of the codebase — always commit them with the related code change
